# Goal — что решено и что осталось

Передача другому чату. Работа начата и **не закончена**; ниже сначала решения (они уже
обсуждены с владельцем продукта, переспрашивать не надо), потом что лежит в коде, потом
что делать.

## Что такое Goal

Контейнер для задач — эпик. Задача либо привязана к цели, либо сама по себе.

Решения, принятые владельцем:

- **Отдельная сущность**, не задача с флагом. Своя таблица, своё имя и описание.
- **Своего статуса нет.** Прогресс считается из задач: сколько закрыто из скольких.
  Хранимого «achieved» нет намеренно — он бы со временем разошёлся с доской, как разошёлся
  бы любой кэш, который никто не пересчитывает.
- **Всё через MCP.** И создание цели, и правка, и привязка задачи. UI по целям — только
  просмотр, как Home.
- **MCP называет цель внутренним id**, не хэндлом вида `RMS-G1` и не именем.
- **Ссылку несёт задача** (`goal_id`), а не цель список задач. Поэтому удаление цели
  ничего не уносит: её задачи читаются как «сами по себе», и если цель с тем же id
  появится снова — они вернутся к ней. Та же снисходительность, что у статуса, типа задачи
  и шаблонов: неизвестное значение читается лениво, а не отвергается.

Экран:

- Сначала цели, под каждой — привязанные к ней задачи.
- Цель можно **свернуть и раскрыть**.
- Задачи без цели показываются под служебной целью **Backlog** (её нет в базе — это группа,
  которую рисует клиент).

## Что уже лежит в коде

Всё перечисленное написано, компилируется и покрыто существующими тестами (45 в rest-api).

| Где | Что |
|---|---|
| `task-manager-shared/src/goals.rs` | `GoalResponse` (с `tasks_amount` / `done_amount`), `GoalsResponse`, `GetGoalsInputModel` |
| `task-manager-shared/src/tasks.rs` | `TaskResponse.goal_id` + `goal_name` |
| `task-manager-rest-api/src/postgres/goals_repo.rs` | таблица `goals`, `get_all` / `upsert` / `delete` |
| `postgres/tasks_repo.rs` | `TaskDto.goal_id` |
| `board/models.rs` | `GoalModel`, `TaskModel.goal_id` |
| `board/board_inner.rs` | `get_goal`, `goals_of_project`, `effective_goal`, `goal_progress`, `put_goal` / `drop_goal` |
| `board/board_state.rs` | `upsert_goal`, `remove_goal` |
| `mappers/goals.rs` | Dto ↔ модель, `goal_to_response` |
| `scripts/tasks.rs` | `goal` в `NewTask` и `TaskPatch`, `resolve_goal` — проверяет, что цель того же проекта |
| `scripts/load_state.rs` | цели читаются на старте |
| `mcp/tasks_write_tool_calls.rs` | свойство `goal` у `tasks_create` и `tasks_update` |

Сейчас это **инертно**: создать цель нечем, поэтому `goal` может только получить отказ.
Компилятор это и показывает — `goals_of_project`, `goal_progress` и `drop_goal` пока никем
не вызваны. Предупреждения о мёртвом коде здесь — маркер незаконченного, а не мусор.

## Что осталось сделать

1. **`scripts/goals.rs`** — create / update / delete. Смотри `scripts/column_templates.rs`
   как образец: валидация целиком до записи, Postgres раньше памяти, `notify_project_changed`
   после. Удаление цели **не** отказывать при наличии задач: они просто станут сами по себе.
2. **MCP-тулы** `goals_list`, `goals_create`, `goals_update`, `goals_delete`. `goals_list`
   возвращает id, имя, описание и прогресс — id нужен агенту, чтобы передать его в
   `tasks_create` / `tasks_update`.
3. **REST**: `POST /api/goals/v1/list` с `projectId` в теле — для экрана.
4. **Экран Goals**: таб сверху, селектор проекта (тот же, что на Home, с запомненным выбором),
   цели с раскрытием, Backlog для задач без цели. Иконка цели уже лежит:
   `task-manager-ui/public/assets/images/goal.svg` — она одним уровнем выше папки типов задач,
   потому что это иконка сущности, а не выбираемая иконка типа.
5. **Промпт MCP** (`mcp/mod.rs`, `INSTRUCTIONS`) — абзац про цели: что это контейнер, что
   называется внутренним id из `goals_list`, что своего статуса у неё нет, и что задача без
   цели — нормальное состояние, а не недоделка.

## Конвенции, которые здесь легко нарушить

Каждая из них уже стоила этому проекту сломанного релиза.

- **Никаких path- и query-параметров.** `#[http_path]` дописывается в конец URL без подстановки
  `{name}`, поэтому маршрут вида `/api/x/{id}/y` сгенерированным клиентом недостижим. А в query
  `+` значит пробел, что уже уничтожало base64-значение. Всё, что зовёт клиент, — `POST` со
  всем в теле. Единственное исключение: `GET /api/system/v1/ping`, это проба живости.
- **Списки живут на `/list`**, потому что создание уже занимает корень коллекции, и два
  POST-хендлера на одном маршруте — коллизия.
- **Снепшот вместо add/remove** там, где редактируется набор: диалог собирает полный список и
  отправляет одним вызовом.
- **Паттерн диалога**: модель внутрь, внутри собирается новая, Save активен только когда они
  различаются, наружу через `EventHandler`; запрос делает обработчик, не диалог.
- **Данные читаются через `DataState`** из `dioxus-utils`, в теле рендера. `use_future` спавнит
  таск один раз и **не** подписывается на сигналы — из-за этого доска не грузилась вообще.
  Реактивны `use_resource`, `use_effect` и чтение `DataState` в рендере.
- **У `<select>` выбранное задаётся атрибутом `selected` у `<option>`**, а не `value` у самого
  селекта, иначе восстановленный выбор не отображается.
- **CSS генерируется**: правь `task-manager-ui/css/*.css`, `public/assets/app.css` перезапишется
  на следующей сборке.
- **Релиз только через `gh release create`**, и сборку проверяй **до** выпуска тега — я один раз
  выпустил неработающую версию, поставив `gh release create` в ту же цепочку, что и `cargo build`.
